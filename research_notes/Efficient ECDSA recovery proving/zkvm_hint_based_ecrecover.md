# Hint-based (non-deterministic advice) ecrecover in zkVMs and zkEVMs — survey notes

Scope: secp256k1 ECDSA public-key recovery / verification in proof systems, with emphasis on which values the host supplies as unchecked advice and how the guest/circuit checks them. Dates and versions are given where the source states them. Numbers from the local ZKsync OS / Airbender checkout are measurements made during this research (2026-10-29) with the user's own, not-yet-published bench crate and are labelled as such.

Research date: 2026-10-29. Roughly 45 web fetches/searches plus local source reads; several primary pages (RISC Zero acceleration page, Succinct patched-crates page, Nexus docs, Jolt runtime-advice page, OpenVM book ECC chapter at its old URL) returned 404/410 or empty content, which is recorded in the Gaps.

## Key question 1 — Which operations are hinted rather than computed, and what does each check cost?

### Takeaway
Every surveyed system hints the same small set of "hard" field operations — modular inverse, field division (slope), square root (decompression), big-integer quotient/remainder — and checks each hint with one or two modular multiplications plus a canonicality (`< modulus`) test. Only Polygon zkEVM (zkASM "free inputs") and the Scroll/halo2-lib circuit hint at the level of every non-native arithmetic quotient; no system was found that hints a scalar multiplication result and verifies it more cheaply than recomputing it.

### Cited Findings

**ZKsync OS / Airbender (`airbender-crypto` secp256k1, oracle hooks)**
- The crypto crate defines a `Secp256k1Hooks` trait with four hintable operations: `fe_sqrt_and_assign`, `fe_invert_and_assign`, `scalar_invert_and_assign`, and `fe_divide` (numerator/denominator adjacent in memory "so that an oracle reads them as one operand"). Two constants steer the algorithms: `FE_INVERT_IS_CHEAP` ("it takes the inverse as a hint and checks it") and `FE_DIVIDE_IS_CHEAP` ("takes the quotient as a hint and checks it with one multiplication. The scalar multiplication then works in affine coordinates, where a group operation is a division (the slope) and two or three multiplications, instead of the 7 to 11 multiplications of the Jacobian formulas"). — [airbender-platform/crates/airbender-crypto/src/secp256k1/hooks.rs (local checkout, commit 68fc0605, 2026-10-02)](file:///Users/alexvlasov/MatterLabs/airbender-platform/crates/airbender-crypto/src/secp256k1/hooks.rs)
- ZKsync OS implements the hooks over its IO oracle (`Secp256k1HooksWithOracle`, both constants `true`). Checks: division — `denominator.mul_in_place(quotient); denominator.sub_in_place(numerator); assert!(denominator.is_zero())` (one multiplication, one subtraction, one zero test; "The denominator is not zero (the caller's obligation), so the quotient is the only element that passes"); inverse — `product.mul_in_place(x); assert!(product.is_one())`; scalar inverse — same; sqrt — the oracle returns `candidate = x^((p+1)/4)` plus a non-residue flag, and the guest checks `candidate² == x` (residue) or `candidate² == -x` (non-residue), which is valid because secp256k1's p ≡ 3 (mod 4) so −1 is a non-residue; zero operands short-circuit (sqrt(0)=0, invert(0)=0). — [zksync-os/basic_system/src/system_functions/field_ops.rs (local, branch av_glamsterdam_support)](file:///Users/alexvlasov/MatterLabs/zksync-os/basic_system/src/system_functions/field_ops.rs)
- The 256-bit field multiplications themselves are not hinted; they go to Airbender's `bigint_with_control` delegation circuit (delegation id 1994 = 0x7ca). ZKsync OS's benchmarking doc weights the proving cost as `effective_cycles = raw_risc_v_cycles + 16 × blake_delegations (id 1991) + 4 × bigint_delegations (id 1994) + 4 × keccak_delegations (id 1995)`. — [zksync-os/docs/benchmarking.md](file:///Users/alexvlasov/MatterLabs/zksync-os/docs/benchmarking.md)
- Per recovery (geth `ecrecover` test vector) the hint-based path makes exactly 192 hint queries: 1 sqrt, 1 scalar inverse, 190 base-field divisions (no base-field inverse queries). — local run of `ecrecover_bench_host` (see KQ3 for the cycle numbers) over [binaries/ecrecover_bench](file:///Users/alexvlasov/MatterLabs/zksync-os/binaries/ecrecover_bench/README.md)

**Succinct SP1 (k256 patch + executor hooks)**
- The SP1 executor registers host "hooks" on file descriptors: `FD_ECRECOVER_HOOK → hook_ecrecover`, `FD_EDDECOMPRESS`, `FD_RSA_MUL_MOD`, `FD_BLS12_381_SQRT`, `FD_BLS12_381_INVERSE`, `FD_FP_SQRT`, `FD_FP_INV`. `hook_ecrecover` takes 65 bytes (curve id 1 = secp256k1 / 2 = secp256r1 plus a `r_is_y_odd` bit, then `r`, then `alpha = r³ + a·r + b`) and returns `[[1], y, r_inv]` if alpha is a square (y parity-adjusted, `r_inv` = inverse of the scalar r) or `[[0], sqrt(NQR·alpha)]` with NQR = 3 otherwise. `hook_fp_inverse` returns the Fermat inverse (panics on zero); `hook_fp_sqrt` takes `[len || element || modulus || nqr]` and returns `[status || root]` (status 1 = root of element, 0 = root of NQR·element). `hook_rsa_mul_mod` returns `[remainder, quotient]`. Doc comments on several hooks say the values "must be constrained by the zkVM for correctness". — [sp1-core-executor 6.2.3 hook.rs](https://docs.rs/crate/sp1-core-executor/6.2.3/source/src/hook.rs)
- In the k256 patch for SP1 6.10.0, `FieldElement::invert` under `cfg(target_os = "zkvm")` calls `crate::call_inv_hook(self.to_bytes(), MODULUS)`, checks hint length and canonicality, then checks `(result * value) - 1 == 0`; failure calls `sp1_lib::invalid_hint!("k256 field inverse: hint did not invert self")`. `sqrt` calls `call_sqrt_hook` with the fixed non-residue `NQR = 3`: status 1 ⇒ check `root² == self`; status 0 ⇒ check `root² == self·NQR` (proof of non-residuosity relative to the constant 3, which is not re-proved at runtime); for status 1 the smaller of the two roots (by byte encoding) is returned. — [sp1-patches k256 field.rs, tag patch-k256-13.4-sp1-6.10.0](https://raw.githubusercontent.com/sp1-patches/elliptic-curves/patch-k256-13.4-sp1-6.10.0/k256/src/arithmetic/field.rs)
- `Scalar::invert` (zkvm) likewise: `call_inv_hook`, length check, canonicality check ("hint is not canonical"), then `result * self != ONE ⇒ invalid_hint!`. — [sp1-patches k256 scalar.rs](https://raw.githubusercontent.com/sp1-patches/elliptic-curves/patch-k256-13.4-sp1-6.10.0/k256/src/arithmetic/scalar.rs)
- `call_inv_hook` / `call_sqrt_hook` build the request inside an `unconstrained!` block (32-byte length prefix, element, modulus, [nqr]), write it to `FD_FP_INV` / `FD_FP_SQRT` with `sp1_lib::io::write`, and read the answer back with `read_vec()`. — [sp1-patches k256 lib.rs](https://raw.githubusercontent.com/sp1-patches/elliptic-curves/patch-k256-13.4-sp1-6.10.0/k256/src/lib.rs)
- `invalid_hint!` halts the zkVM with exit code 3 ("invalid prover hint"), distinct from panic exit code 1, so that "a malicious prover cannot forge a panicked-program proof by feeding wrong hints". — [sp1-lib docs, macro invalid_hint](https://docs.rs/sp1-lib/latest/sp1_lib/macro.invalid_hint.html)
- Point decompression in `sp1_lib::ecdsa::affine` computes `alpha = x³ + a·x + b; beta = alpha.sqrt()` (the sqrt is the hinted one above) and chooses the sign by parity; field elements are canonical "by virtue of being created via `FromBytes`". Curve additions/doublings are syscalls: `syscall_secp256k1_add`, `syscall_secp256k1_double`, `syscall_secp256k1_decompress`; `syscall_hint_len`/`syscall_hint_read`, `syscall_enter_unconstrained`/`syscall_exit_unconstrained` are the generic hint/unconstrained primitives. — [sp1-lib affine.rs](https://docs.rs/crate/sp1-lib/latest/source/src/ecdsa/affine.rs); [sp1-lib lib.rs](https://docs.rs/crate/sp1-lib/latest/source/src/lib.rs)
- Older sp1-lib (1.2.0) documents the design intent: the `unconstrained` macro "Executes a block of code unconstrained by the VM"; running ecrecover inside the VM is costly but verifying a signature is cheap once the public key is known, so `unconstrained` can supply the public key "without spending VM CPU cycles". — [sp1-lib 1.2.0](https://docs.rs/sp1-lib/1.2.0)

**RISC Zero (patched k256 + `sys_bigint` / `bigint2`)**
- The `risc0-bigint2` crate (v1.4.14, Apache-2.0) exposes checked field ops `modadd/modsub/modmul_{256,384}`, `modmul_4096`, `modinv_{256,384}`, degree-2/4 extension ops, and EC `add`/`double`/`mul` via `sys_bigint2_3` / `sys_bigint2_4` program blobs (`ec_add_256.blob`, `ec_double_256.blob`). Every checked op carries the comment that an honest host returns a reduced result but "a dishonest prover can sometimes return a result greater than the prime", so the wrapper asserts `result < modulus`; an `unchecked` submodule omits the check "where these restrictions aren't necessary for security". `modinv` notes that if no inverse exists "no proof can be generated" and the executor panics. — [risc0-bigint2 field/mod.rs](https://docs.rs/risc0-bigint2/latest/src/risc0_bigint2/field/mod.rs.html); [risc0-bigint2 ec/mod.rs](https://docs.rs/risc0-bigint2/latest/src/risc0_bigint2/ec/mod.rs.html)
- EC layer: `add_internal` handles identity, `P + (−P)` (same x, different y ⇒ identity) and `P + P` (⇒ `double_raw`) in software before calling the raw precompile ("otherwise this function will panic in the host"); `mul` is plain double-and-add over the scalar bits, "assumes `self` is on the curve … isn't checked here", and "doesn't work if `scalar` is a multiple of `pt`'s order"; outputs are asserted `< prime`. — [risc0-bigint2 ec/mod.rs](https://docs.rs/risc0-bigint2/latest/src/risc0_bigint2/ec/mod.rs.html)
- Patched crates listed for ECDSA: `k256` 0.13.1–0.13.4 (tag `k256/v0.13.3-risczero.1`, requires the `unstable` feature and risc0 ≥ 1.2.0), `crypto-bigint` 0.5.x, `sha2`; revm's default k256 backend is patched but its `secp256k1` feature uses the unpatched `secp256k1` crate. The page warns precompiles are not constant-time. — [dev.risczero.com precompiles](https://dev.risczero.com/api/zkvm/precompiles)
- Third-party RISC Zero project `secp256k10` (l2iterative): host supplies `r_inv` (guest checks `r_inv·r = 1`), a "square root of an imaginary square root" as the Legendre-symbol proof, and the slope of every doubling/addition so the guest "checks it without doing inversions"; hints are streamed as host input. For GLV it needs `⌊a·b/n⌋` and obtains it from two `sys_bigint` calls, `r = a·b mod n` and `r' = a·b mod (n−1)`, picking the quotient from the comparison of `r` and `r'` — a trick proven in Coq (`coq/quotient.v`). — [l2iterative/secp256k10 README](https://github.com/l2iterative/secp256k10)

**OpenVM (modular-arithmetic + ECC extensions)**
- The algebra guest library documents `DivUnsafe::div_unsafe` as "Division operation that is undefined behavior when the denominator is not invertible" and `Sqrt` as "Note that we use a hint-based approach to prove whether the square root exists" (prime moduli only); `assert_reduced` exists because "guest code does not have to use the unique representation below the modulus" and must enforce it where it matters; `HintNonQr` and `HintSqrt` are funct7 variants of the modular-arithmetic opcode. — [openvm-algebra-guest lib.rs](https://docs.rs/crate/openvm-algebra-guest/latest/source/src/lib.rs); [DivUnsafe trait doc](https://docs.rs/openvm-algebra-guest/latest/openvm_algebra_guest/trait.DivUnsafe.html)
- ECC extension (internal audit, commit `4285a4f`): a non-quadratic-residue is hinted in each curve's setup function and stored as a global; decompression either succeeds or "proves no curve point has that x-coordinate" via a hinted `sqrt(rhs · nonqr)`; the guest verifies that the non-QR really is a non-residue and that hinted elements are below the modulus, and "enters an infinite loop" on a bad hint so a malicious host cannot prove a panic. — [OpenVM audits/v1/v1-internal/extension-ecc.md](https://github.com/openvm-org/openvm/blob/main/audits/v1/v1-internal/extension-ecc.md)
- `sw_declare!` decompress: `y = (x³ + a·x + b).sqrt()`, parity fix-up, `from_xy_unchecked`, with the comment "In order for sqrt() to return Some, we are guaranteed that y * y == y_squared, which already proves (x, correct_y) is on the curve". Setup issues two `SwSetup` instructions (modulus and `a`). — [openvm-ecc-sw-macros lib.rs](https://docs.rs/crate/openvm-ecc-sw-macros/latest/source/src/lib.rs)
- `openvm-ecc-guest` `recover_from_prehash_noverify`: rejects wrong signature length, `r == 0 || s == 0`, non-canonical `r`,`s` (`from_be_bytes(...).ok_or_else`), adds `C::ORDER` to `r` when the recovery id says x was reduced (`checked_add`, overflow ⇒ Err), decompresses `R`, computes `neg_u1 = z.div_unsafe(&r)`, `u2 = s.div_unsafe(&r)` (hinted divisions), then `msm(&[neg_u1, u2], &[NEG_G, R])`; the identity result is rejected by `VerifyingKey::from_affine`. Message hash: "we don't need to reduce because IntMod is up to modular equivalence". — [openvm-ecc-guest ecdsa.rs](https://docs.rs/crate/openvm-ecc-guest/latest/source/src/ecdsa.rs)
- Add/double in `weierstrass.rs`: generic `add_assign_impl` handles identity, `x1 == x2 ∧ y1 + y2 == 0 ⇒ identity`, equal ⇒ double, else `add_ne` (precondition "Assumes self != +- p2 and self != identity and p2 != identity"); double assumes `self != identity and 2·self != identity`. Slopes are `div_unsafe`. — [openvm-ecc-guest weierstrass.rs](https://docs.rs/crate/openvm-ecc-guest/latest/source/src/weierstrass.rs)

**Jolt (advice + inlines)**
- Jolt distinguishes `UntrustedAdvice<T>` (prover-committed, "The proof system does not constrain prover-supplied advice, so the guest must check that the advice has the properties the program relies on") from `TrustedAdvice<T>` (verifier holds an externally produced commitment) and runtime advice via `#[jolt::advice]` functions, recommended when "checking the result is cheaper than computing it", with modular inverse as the canonical example. — [Jolt book, guests](https://jolt.a16zcrypto.com/usage/guests_hosts/guests.html)
- The secp256k1 inline set (opcode 0x0B, funct7 0x05) is: `SECP256K1_MULQ`, `SQUAREQ`, `DIVQ` (base field), `MULR`, `SQUARER`, `DIVR` (scalar field), and `SECP256K1_GLVR_ADV` — "pure non-deterministic advice" returning `(s1, |k1|, s2, |k2|)` with `k = k1 + k2·λ (mod r)`, `|k1|,|k2| ≤ 2^128`; the division inlines compute `c` such that `c·b − w·q = a`, i.e. the quotient and the Montgomery/reduction witness are supplied and checked by one multiplication identity. There are no add/sub inlines. — [a16z/jolt jolt-inlines/secp256k1/src/lib.rs](https://raw.githubusercontent.com/a16z/jolt/main/jolt-inlines/secp256k1/src/lib.rs); [Jolt book, inlines](https://jolt.a16zcrypto.com/how/optimizations/inlines.html)
- Inlines expand to native RISC-V instruction sequences (virtual registers 48–127, 64-bit immediates, custom instructions with structured MLEs) instead of separate precompile tables; failing checks can be surfaced as `Result`, `unwrap()` (provable panic) or `unwrap_or_spoil_proof()` (proof becomes unsatisfiable, "suits asserting that a signature is valid"). — [Jolt book, inlines](https://jolt.a16zcrypto.com/how/optimizations/inlines.html)

**Polygon zkEVM (zkASM free inputs)**
- `ecrecover.zkasm` obtains `r_inv` from `invFnEc`, `y` from `sqrtFpEc` (returns the root and a has-root flag; when no root exists `checkSqrtFpEc` must return 1 "or the proof fails"), `k1·G + k2·R` from `mulPointEc`, and products from `mulFpEc`/`mulFnEc`; every hinted quantity is "alias"-checked (asserted `< FNEC`) and `y² = r³ + 7` is re-derived from `r`; `y` parity must match `v` "otherwise the code asserts and the prover is treated as malicious". — [zkevm-rom main/ecrecover/ecrecover.zkasm](https://raw.githubusercontent.com/0xPolygonHermez/zkevm-rom/main/main/ecrecover/ecrecover.zkasm)
- The USENIX Security '25 paper on Polygon zkEVM free inputs: free inputs come from "an unconstrained command evaluator", writing their constraints "demands strong mathematical expertise"; the authors introduce the "dual execution path attack" and FreeVer, which "detected 7 new vulnerabilities" (all confirmed high impact via the bounty). — [USENIX Sec '25, Peng et al.](https://www.usenix.org/conference/usenixsecurity25/presentation/peng-xinghao)

**Scroll zkEVM (halo2-lib ECDSA chip)**
- Scroll's `sig_circuit` calls halo2-ecc's `ecdsa_verify_no_pubkey_check` with the public key supplied as a private witness (checked `is_on_curve_or_infinity`), i.e. the key is hinted and the signature verified against it; `v` is a witness bit tied to `y` via `y = 2·y_tmp + v` with `y_tmp` an 87-bit range-checked witness; halo2-ecc config is 56 advice columns, 8 lookup-advice columns, 1 fixed column, 19 lookup bits, 3 × 88-bit limbs; keccak table lookup uses 3 rows per signature. — [scroll-tech/zkevm-circuits sig_circuit.rs](https://raw.githubusercontent.com/scroll-tech/zkevm-circuits/develop/zkevm-circuits/src/sig_circuit.rs)
- In `ecdsa_verify_no_pubkey_check`, `u1 = msghash / s` and `u2 = r / s` use `divide_unsafe` (witness quotient); `u1`,`u2` are range-checked `< n`; `u1·G` is a fixed-base windowed multiplication and `u2·pubkey` variable-base windowed; the two partial sums are checked not to be negatives of each other (`x_neq OR y_eq`), summed, and `x1` is `enforce_less_than(n)` then compared to `r` with `big_is_equal`. The function returns a bit that the caller must constrain; the x-coordinate is not reduced mod n, so signatures with `x ∈ [n, p)` are rejected ("only valid when `p` is very close to `n`"). — [halo2-ecc ecc/ecdsa.rs](https://docs.rs/halo2-ecc/latest/src/halo2_ecc/ecc/ecdsa.rs.html)

### Inferences
- Across all systems the per-hint check cost is one modular multiplication (plus a subtraction/compare) for inverse, division and sqrt, and one 256×256-bit multiplication plus a comparison for quotient/remainder hints. In Airbender terms a check is a single `bigint_with_control` delegation (4 effective cycles) plus the control flow around it.
- Hinting the division (slope) rather than the inverse is what unlocks affine group operations: one hinted division + 2–3 multiplications per group op versus 7–11 multiplications in Jacobian coordinates (airbender-crypto doc comment). ZKsync OS, l2iterative/RISC Zero (hinted slopes), Jolt (`DIVQ` inline) and OpenVM (`div_unsafe` in `add_ne`) all do this; SP1's AIR chips and RISC Zero's `ec_add` blob do the equivalent inside the precompile circuit (not visible from the guest side).
- The "proof of non-residuosity" differs: SP1 relies on a hardcoded NQR = 3 (not re-proved), OpenVM hints a NQR and verifies it at setup, ZKsync OS exploits p ≡ 3 (mod 4) by requiring `candidate² = −x` (no separate NQR needed), Polygon has a dedicated `checkSqrtFpEc` routine.

## Key question 2 — Does any system hint the whole scalar-multiplication result or intermediate points, and how is it verified?

### Takeaway
No surveyed system hints `u1·G + u2·R` itself and verifies it with a cheaper check — verification of an arbitrary scalar multiple is as expensive as computing it. What is hinted at the point level is (a) the recovered public key in signature-verification form (Scroll's sig circuit, SP1's `unconstrained` design note) — which replaces recovery by verification at essentially the same EC cost — and (b) per-step slopes/quotients, which turn each intermediate point computation into a few multiplications.

### Cited Findings
- Scroll's signature circuit takes the public key `(x, y)` as a private witness, checks it is on the curve, verifies the ECDSA signature against it with `ecdsa_verify_no_pubkey_check`, and derives the address by keccak-table lookup; recovery is never performed in-circuit. — [scroll-tech/zkevm-circuits sig_circuit.rs](https://raw.githubusercontent.com/scroll-tech/zkevm-circuits/develop/zkevm-circuits/src/sig_circuit.rs)
- SP1's early `unconstrained` documentation gives ecrecover as the motivating case: the public key can be supplied unconstrained and then verified in the VM. — [sp1-lib 1.2.0](https://docs.rs/sp1-lib/1.2.0)
- The current SP1 ecrecover path does not hint the key: `hook_ecrecover` returns only `y` (decompression) and `r_inv`, and the guest computes the key by syscall-accelerated double-and-add. The `multi_scalar_multiplication` in sp1-lib iterates over all 256 bit positions of both scalars, adding `temp_a`/`temp_b` when bits are set and doubling both every iteration — "2L doublings and up to 2L additions", no shared doublings, no precomputed `a + b`. `weierstrass_add_assign` handles infinity / equal / inverse cases in software (5 cases). — [sp1-core-executor hook.rs](https://docs.rs/crate/sp1-core-executor/6.2.3/source/src/hook.rs); [sp1-lib utils.rs](https://docs.rs/crate/sp1-lib/latest/source/src/utils.rs)
- l2iterative/secp256k10 hints every intermediate slope ("the slope for each doubling and addition"); the guest checks the slope relation without inversions, so intermediate points are computed from hinted slopes, not hinted themselves. — [l2iterative/secp256k10](https://github.com/l2iterative/secp256k10)
- airbender-crypto's affine path computes the intermediate points from hinted quotients and includes a fused "doubling followed by an addition, `2r + p`, computed as `(r + p) + r` without the `y` of the intermediate point" (two divisions, two squarings, one multiplication); "All the formulas are complete here: the inputs of `ecrecover` are chosen by the caller of the precompile, so an accumulator equal to the point to add, or to its negation, is reachable. Every division has its denominator tested". — [airbender-crypto recover_affine.rs (local)](file:///Users/alexvlasov/MatterLabs/airbender-platform/crates/airbender-crypto/src/secp256k1/recover_affine.rs)
- SP1 PR #2719 (RFC, 2026-04-14) proposes `SEPTIC_SCALAR_MUL` / `SEPTIC_VERIFY` precompiles for Schnorr on SP1's internal septic curve (not secp256k1) and reports a ~325× reduction versus composing add/double syscalls — the only "whole scalar-mul as one precompile" proposal found, and its AIR constraints "are not implemented". — [succinctlabs/sp1 PR 2719](https://github.com/succinctlabs/sp1/pull/2719)
- Jolt hints the GLV decomposition `(k1, k2)` of a scalar (`SECP256K1_GLVR_ADV`), not the product. — [a16z/jolt secp256k1 inline](https://raw.githubusercontent.com/a16z/jolt/main/jolt-inlines/secp256k1/src/lib.rs)

### Inferences
- Hinting the recovered key `Q` and verifying `(u1·G + u2·Q).x == r` costs the same two scalar multiplications as recovery (`u1·G + u2·R`); its only savings are the sqrt/decompression of `R` (one hint anyway) and, in circuit settings, avoiding a data-dependent branch on "no square root exists". In zkVM settings the verification form additionally needs an explicit identity/`x ∈ [n, p)` treatment that recovery gets for free, which is why SP1, OpenVM and ZKsync OS all recover rather than verify.
- A "witnessed point lies on the line" check (verify a hinted sum `P3` by checking collinearity `λ(x1 − x3) = y1 + y3` and `λ² = x1 + x2 + x3`) is exactly what hinting the slope achieves: it is 2–3 multiplications per group op and is the ceiling of what hints buy per step. Verifying a full multiple `kP` cheaper than that would need a pairing or a batch argument; none of the surveyed systems has one for secp256k1.

### Gaps
- No public write-up was found of a zkVM batching many ecrecovers into one argument (e.g. random-linear-combination of verification equations) for secp256k1; the Anoma report only suggests "aggregate multiple delta proofs into a single signature" as the remaining lever ([forum.anoma.net](https://forum.anoma.net/t/execution-proof-performance-report/2654)).

## Key question 3 — Reported ecrecover costs (cycles / rows / time) with and without precompiles or hints, 2024–2026

### Takeaway
With precompiles and hints a secp256k1 recovery costs roughly 50–75 k RISC-V cycles in SP1 (plus ~780 syscall rows), ~650 k cycles in RISC Zero (dominated by `sys_bigint`/`bigint2` syscalls), and in the ZKsync OS / Airbender stack ~66 k raw cycles plus ~7.5 k bigint delegations (hints on) versus ~117 k cycles plus ~21.6 k delegations (hints off) and ~2.1 M cycles in pure software; Polygon zkEVM reports 528 arithmetic-SM operations and ~6.3 k main-SM steps per recovery.

### Cited Findings

**ZKsync OS / Airbender — local measurement (uncommitted bench crate, airbender-crypto commit 68fc0605, run 2026-10-29, geth test vector, deterministic cycle counts)**

## Key question 4 — Techniques that cut the number of EC group operations below the usual GLV ~128 doublings + additions when hints are available

### Takeaway
With cheap hinted divisions the win is not fewer group operations but cheaper ones (affine, 1 division + 2–3 multiplications, fused `2r+p`); the operation count is reduced by the classical means — GLV splitting of both scalars, wide wNAF or fixed windows over precomputed affine tables of `G` and `2^128·G`/`φ(G)`, joint (Straus–Shamir) tables for the variable point — giving ≈ 190 group operations per recovery in airbender-crypto, versus SP1's ≈ 780.

### Cited Findings
- airbender-crypto default structure: "wNAF-5 over 8 odd multiples of `A` and `phi(A)` with the same effective `z`, and wNAF-10 over tables of `G` and `2^128*G`"; `ECMULT_TABLE_SIZE_A = 1 << (WINDOW_A − 2)`, generator tables `pre_g`, `pre_g_128` of size `1 << (WINDOW_G − 2)` built at compile time (static context, derived from libsecp256k1). With `FE_INVERT_IS_CHEAP` the odd-multiples table of `A` is made affine by a single hinted inversion (`table_set_affine_windowa`) instead of carrying a shared denominator. — [recover.rs, context.rs (local)](file:///Users/alexvlasov/MatterLabs/airbender-platform/crates/airbender-crypto/src/secp256k1/recover.rs)
- Alternative structure in the same crate (`recover_shamir.rs`, "the one used by evmone's `ecrecover` on Airbender (`ecrecover_msm_glv`)"): both scalars GLV-split into ~128-bit halves; `ng·G` uses fixed unsigned 8-bit windows over precomputed affine tables of `G` and `φ(G)` — "16 additions per half, no odd-multiples tables or wNAF" (tables of 255 entries, 17 windows); `na·A` uses the joint NAF of the two halves with the table `{A, φ(A), A+φ(A), A−φ(A)}`; because inversion is a hint, both combined entries are kept affine. — [recover_shamir.rs (local)](file:///Users/alexvlasov/MatterLabs/airbender-platform/crates/airbender-crypto/src/secp256k1/recover_shamir.rs)
- Fused step in the affine path: `2r + p` as `(r + p) + r` without computing the intermediate `y`; slope of the second addition is `−(λ1 + 2·y_r/(x_t − x_r))`: "two divisions, two squarings and one multiplication" for a doubling-plus-addition. — [recover_affine.rs (local)](file:///Users/alexvlasov/MatterLabs/airbender-platform/crates/airbender-crypto/src/secp256k1/recover_affine.rs)
- l2iterative/secp256k10: "a larger lookup table is precomputed, so no doublings are needed for G-multiplications"; for the dynamic point a joint table of size 15 with unsigned 4-bit slicing; GLV decomposition uses ceiling instead of rounding (vector may be slightly larger); baseline patched k256 uses 8-entry tables, signed 4-bit windows (32 windows), doublings merged into the GLV step. — [l2iterative/secp256k10](https://github.com/l2iterative/secp256k10)
- Jolt: GLV decomposition is advice (`SECP256K1_GLVR_ADV`), so the guest only checks `k = k1 + k2·λ (mod r)` and the 128-bit bounds rather than running the lattice reduction; P-256 uses a "Fake GLV" advice. — [a16z/jolt secp256k1 inline](https://raw.githubusercontent.com/a16z/jolt/main/jolt-inlines/secp256k1/src/lib.rs); [Jolt book, inlines](https://jolt.a16zcrypto.com/how/optimizations/inlines.html)
- OpenVM's `CachedMulTable` is a fixed-window method with `2^w − 2` stored multiples per base, `window_bits` dividing 8, ≈ `(num_windows − 1) × window_bits` doublings plus one addition per base per window. — [openvm-ecc-guest weierstrass.rs](https://docs.rs/crate/openvm-ecc-guest/latest/source/src/weierstrass.rs)
- Polygon zkEVM's `mulPointEc` computes `k1·G + k2·R` at 528 arith operations per recovery on the with-root path. — [ecrecover.zkasm](https://raw.githubusercontent.com/0xPolygonHermez/zkevm-rom/main/main/ecrecover/ecrecover.zkasm)
- SP1 PR #2719 quantifies Shamir's trick on its septic curve: ≈ 381 EC operations versus ≈ 651 for two separate scalar multiplications. — [succinctlabs/sp1 PR 2719](https://github.com/succinctlabs/sp1/pull/2719)

### Inferences
- The 190 hinted divisions per recovery measured in the ZKsync OS stack correspond to about 128 doublings (shared by the GLV halves, each doubling one division) plus ≈ 60 additions (wNAF-5 density ≈ 1/6 per half for `A`, wNAF-10 density ≈ 1/11 per half for `G`), with the fused `2r+p` step turning some doubling+addition pairs into two divisions. Hints therefore do not lower the op count; they make each op ≈ 3–4 multiplications.
- Below ~128 doublings the only remaining levers are (i) larger fixed tables for `G` (l2iterative: zero doublings for `G`, evmone: 8-bit windows), (ii) interleaving the variable point with the generator so the 128 doublings are shared (already done), and (iii) hinting the GLV decomposition (Jolt). Hinting cannot remove the ~128 doublings of the variable point `R`.

### Gaps
- No source gives a measured group-operation count for an SP1 or OpenVM recovery; the SP1 figure (≈ 780) is inferred from syscall counts.
- The relative cost of airbender-crypto's two MSM structures (wNAF vs. evmone-style fixed windows) was not measured here; the crate's comment says the Shamir variant "exists to compare the two structures".

## Key question 5 — Known soundness pitfalls of hint-based ecrecover

### Takeaway
Documented failure modes are: non-canonical (unreduced) hint values, missing `r`/`s`/coordinate range checks, "proof of failure" paths that a malicious host can trigger on valid inputs (panic/unprovable instead of `Err`), incomplete addition formulas at caller-controlled edge cases, hinted auxiliary values that are only checked for non-zero rather than for the property the optimisation needs (OpenVM pairing CVE), and divergence between transaction-signature rules (low-s) and precompile rules.

### Cited Findings
- **Unreduced hint outputs.** RISC Zero `bigint2`: "a dishonest prover can sometimes return a result greater than the prime", hence `assert!(result < modulus)` in every checked op and the EC wrappers; an `unchecked` module exists for callers who know it is safe. — [risc0-bigint2 field/mod.rs](https://docs.rs/risc0-bigint2/latest/src/risc0_bigint2/field/mod.rs.html); [ec/mod.rs](https://docs.rs/risc0-bigint2/latest/src/risc0_bigint2/ec/mod.rs.html). SP1's k256 patch explicitly rejects non-canonical inverse hints ("hint is not canonical"). — [sp1-patches scalar.rs](https://raw.githubusercontent.com/sp1-patches/elliptic-curves/patch-k256-13.4-sp1-6.10.0/k256/src/arithmetic/scalar.rs). OpenVM documents that guest integers need not be in canonical form and provides `assert_reduced`/`is_reduced` for the places where uniqueness matters. — [openvm-algebra-guest](https://docs.rs/crate/openvm-algebra-guest/latest/source/src/lib.rs). Polygon zkASM asserts every hinted value "alias-free" (`< FNEC`). — [ecrecover.zkasm](https://raw.githubusercontent.com/0xPolygonHermez/zkevm-rom/main/main/ecrecover/ecrecover.zkasm)
- **Malicious host forcing a provable failure on valid inputs.** OpenVM internal ECC audit finding 2.3 (High): "Malicious host can make decompress panic" — invalid hints could make a valid point's decompression panic, letting the host prove a panic that an honest run would not produce; fix: guests loop forever on bad hints. Finding 2.4 (High): out-of-range `r`/`s` made the circuit unprovable (via the `iseqmod` intrinsic) instead of returning `Error`; fixed with a byte-wise `is_reduced()` check returning `Error` outside `[1, n)`. Finding 2.5 (High): `find_non_qr` broken for p ≡ 1 (mod 4). — [OpenVM extension-ecc audit](https://github.com/openvm-org/openvm/blob/main/audits/v1/v1-internal/extension-ecc.md). SP1 addresses the same class with `invalid_hint!` (exit code 3 ≠ panic code 1) so "a malicious prover cannot forge a panicked-program proof by feeding wrong hints". — [sp1-lib invalid_hint](https://docs.rs/sp1-lib/latest/sp1_lib/macro.invalid_hint.html)
- **Hinted auxiliary value checked only for non-zero.** OpenVM `openvm-pairing` (CVE-2026-46669, fixed in 1.6.0, found by zkSecurity's zkao, Critical): the final-exponentiation shortcut takes a hint `c` and a scaling factor and checks `f·u = c^λ`, but only tested `c ≠ 0` and never that the scaling factor lies in the F_p6 subfield; a prover can set `c = 1`, `u = f⁻¹` and pass any pairing check, forging KZG/Groth16/`ecPairing` results. Same pattern applies to any hint whose relation is sound only under an unchecked side condition. — [blog.zksecurity.xyz/posts/openvm-bugs](https://blog.zksecurity.xyz/posts/openvm-bugs/)
- **Free inputs in Polygon zkEVM.** Hexens' audit found "a discrepancy with how ecrecover is implemented in zkASM … could have allowed a dishonest user to generate a proof for a transaction that is not compliant with the EVM". — [polygon.technology blog](https://polygon.technology/blog/polygon-zkevm-results-of-hexens-security-audit) (only the search snippet was retrievable; the page returned 404). The USENIX '25 FreeVer paper found 7 new free-input vulnerabilities and names the "dual execution path attack" (an under-constrained free input lets honest and malicious provers follow different paths, e.g. different square roots, causing chain splits). — [USENIX Sec '25](https://www.usenix.org/conference/usenixsecurity25/presentation/peng-xinghao)
- **Incomplete group-law edge cases reachable from caller input.** airbender-crypto: "the inputs of `ecrecover` are chosen by the caller of the precompile, so an accumulator equal to the point to add, or to its negation, is reachable. Every division has its denominator tested, and a zero sends the step to the case it stands for". — [recover_affine.rs (local)](file:///Users/alexvlasov/MatterLabs/airbender-platform/crates/airbender-crypto/src/secp256k1/recover_affine.rs). OpenVM's `add_ne`/`double_nonidentity` intrinsics document preconditions (`self != ±p2`, non-identity, `2·self != identity`) that the generic wrapper must enforce; the book warns deserialized points are not checked on-curve and `VerifyingKey::from_affine` rejects identity and non-canonical coordinates "but does not check the curve equation". — [openvm-ecc-guest weierstrass.rs](https://docs.rs/crate/openvm-ecc-guest/latest/source/src/weierstrass.rs); [OpenVM book, ECC (v2.0.2)](https://docs.openvm.dev/book/acceleration-using-extensions/elliptic-curve-cryptography). RISC Zero's `mul` "doesn't work if `scalar` is a multiple of `pt`'s order" and does not check on-curve. — [risc0-bigint2 ec/mod.rs](https://docs.rs/risc0-bigint2/latest/src/risc0_bigint2/ec/mod.rs.html). Jolt PR #1402 (merged 2026-04-16) moved scalar range (`z, r, s < n`), coordinate range (`< p`) and on-curve checks into `ecdsa_verify()` because relying on callers was "a security footgun" (issue #1391). — [a16z/jolt PR 1402](https://github.com/a16z/jolt/pull/1402)
- **Non-residuosity proofs.** SP1 relies on the compile-time constant NQR = 3 ("3 is a NQR of the secp256k1 base field") and does not re-prove it; OpenVM hints the NQR and verifies it at setup; ZKsync OS requires `candidate² = −x`. A wrong or unverified NQR would let a prover claim "no square root" for a valid `r`, i.e. make a valid signature unrecoverable (completeness/censorship rather than forgery). — [sp1-patches field.rs](https://raw.githubusercontent.com/sp1-patches/elliptic-curves/patch-k256-13.4-sp1-6.10.0/k256/src/arithmetic/field.rs); [OpenVM audit](https://github.com/openvm-org/openvm/blob/main/audits/v1/v1-internal/extension-ecc.md); [field_ops.rs (local)](file:///Users/alexvlasov/MatterLabs/zksync-os/basic_system/src/system_functions/field_ops.rs)
- **x-coordinate in `[n, p)` and reduction mod n.** halo2-lib's `ecdsa_verify_no_pubkey_check` enforces `x1 < n` instead of reducing, so valid signatures with `x1 ∈ [n, p)` are rejected (accepted because `1/(p−n)` is tiny for secp256k1); the function also returns an unconstrained bit the caller must assert. — [halo2-ecc ecdsa.rs](https://docs.rs/halo2-ecc/latest/src/halo2_ecc/ecc/ecdsa.rs.html). OpenVM reconstructs `x = r + n` when the recovery id says x was reduced, with `checked_add` overflow ⇒ `Err`. — [openvm-ecc-guest ecdsa.rs](https://docs.rs/crate/openvm-ecc-guest/latest/source/src/ecdsa.rs). An ethresear.ch note observes that the EVM precompile cannot cover the full key space because "ecrecover fails if r >= N". — [ethresear.ch](https://ethresear.ch/t/you-can-kinda-abuse-ecrecover-to-do-ecmul-in-secp256k1-today/2384)
- **Malleability / low-s rules differ by context.** Polygon's zkASM uses `ecrecover_s_upperlimit = FNEC−1` for the precompile path and `FNEC/2` for the transaction path. — [ecrecover.zkasm](https://raw.githubusercontent.com/0xPolygonHermez/zkevm-rom/main/main/ecrecover/ecrecover.zkasm). A 2023 Code4rena finding against zkSync Era's `Ecrecover.yul` argued its handling of high-`s` values diverged from Ethereum clients (the finding's claim that clients reject high-s in the *precompile* conflicts with Polygon's two-limit implementation; treat the client-behaviour claim with caution). — [Code4rena 2023-03 zkSync issue 190](https://vulners.com/code423n4/CODE423N4:2023-03-ZKSYNC-FINDINGS-ISSUES-190)
- **Precompile-table divergence (not hint-specific).** An Immunefi report against Base's ZK proof program flagged a non-canonical precompile table as a soundness break. — [reports.immunefi.com](https://reports.immunefi.com/base/75347-bc-medium-zk-proof-program-uses-a-non-canonical-precompile-table-breaking-soundness-across-eve)
- **Fiat–Shamir binding of public values (not hint-specific but affects the same proofs).** OtterSec's March 2026 write-up lists six zkVMs (Jolt, Nexus, Cairo-M, Ceno, Expander, Binius64) whose verifiers did not bind prover-supplied public claims before deriving challenges; all were fixed between Oct 2025 and Mar 2026. — [osec.io](https://osec.io/blog/2026-03-03-zkvms-unfaithful-claims/)

### Inferences
- The recurring design rule across SP1, OpenVM and ZKsync OS is: a failed hint check must never be representable as an honest program outcome — SP1 uses a distinct exit code, OpenVM loops forever, ZKsync OS `assert!`s (panic in the guest, which in the Airbender setting means no valid proof). Any system that lets a bad hint surface as `Err`/`None` creates the OpenVM-2.3 class of censorship bug.
- Hints that are "checked by multiplication" are sound only when the checked equation has a unique solution in the canonical domain: division needs the denominator non-zero (ZKsync OS makes it the caller's obligation and tests it in the complete formulas; OpenVM calls it UB), inverse needs canonicality (SP1 checks), sqrt needs a specified root choice (SP1 picks the smaller encoding; ZKsync OS and Polygon fix parity against `v`).

### Gaps
- No public post-mortem of an exploited (not merely audited) hint bug in a secp256k1 ecrecover path was found; the closest exploitable example is the OpenVM pairing hint (BN254/BLS12-381), and the Polygon/Hexens ecrecover finding has no retrievable technical detail.
- The Linea audit item "Incomplete Constraint in ECRecover Precompiled Contract" (Least Authority, 2024) appeared only as a title in search results; its content was not retrieved.
- ZKsync OS's own audit PDFs in `zksync-os/audits/` (Taran crypto review 2025-10, OpenZeppelin 2025-09, Audittens) could not be text-extracted in this environment (no poppler); any ecrecover-hook findings there are unverified.
